## 1. System Overview

QueueStorm Investigator is a **Hybrid Rules-First + AI-Inference Pipeline** deployed as Vercel Serverless Functions.

The core philosophy: **Deterministic logic owns all structural decisions. The LLM only writes human-readable text.**

This means:
- `relevant_transaction_id` — computed by the Rules Engine, never overrideable by AI
- `evidence_verdict` — computed by the Rules Engine, never overrideable by AI
- `case_type`, `department`, `severity`, `human_review_required` — computed by the Rules Engine (AI provides a suggestion that is overwritten if the rules engine has a confident answer)
- `agent_summary`, `recommended_next_action`, `customer_reply` — generated by Groq/Llama, then passed through a deterministic safety sanitizer

```
Request

┌─────────────────────────────────┐
```

## 2. Layer-by-Layer Deep Dive

### Layer 1: Schema Validation (Zod)

File: `lib/schema.ts`

Every request is parsed by `TicketRequestSchema` before any logic runs:
- Missing `ticket_id` or `complaint` → HTTP `400` immediately
- Invalid enum values (e.g. `language: 'fr'`) → HTTP `400`
- Whitespace-only `complaint` → HTTP `422`
- All transaction history fields are type-validated

This guarantees the service **never crashes on malformed input** (10% reliability score).

### Layer 2: Rules Engine

File: `lib/rules-engine.ts`

This is the heart of the investigator. It runs 6 independent deterministic sub-modules:

#### 2a. Safety & Injection Detection (ALWAYS FIRST)

```
PHISHING_KEYWORDS + pattern matching → is_phishing_complaint
INJECTION_PATTERNS (regex) → is_prompt_injection
CREDENTIAL_REQUEST_KEYWORDS → has_credential_mention
```

If `is_prompt_injection = true`, the LLM is **skipped entirely** and a hardcoded safe response is returned. This makes prompt injection resistance mathematically guaranteed — not LLM-dependent.

#### 2b. Case Type Detection (Priority-Ordered)

Detection priority (critical correctness: later checks must not shadow earlier ones):
1. `phishing_or_social_engineering` (always highest priority)
2. `duplicate_payment` (requires BOTH keyword + data evidence — prevents false positives)
3. `merchant_settlement_delay` (checked BEFORE wrong_transfer to prevent "not received" being misclassified)
4. `agent_cash_in_issue`
5. `wrong_transfer`
6. `payment_failed`
7. `refund_request`
8. `null` → LLM decides, falls back to `other`

#### 2c. Transaction Matching Algorithm

Scoring per transaction:

| Signal | Points |
|--------|--------|
| Amount in complaint matches txn amount (±0) | +10 |
| Counterparty phone in complaint (last 7 digits) | +8 |
| Transaction ID explicitly mentioned | +15 |
| Time mention aligns with txn timestamp (±2h) | +5 |
| "today" mentioned + txn < 24h old | +3 |
| "yesterday" + txn 24-48h old | +3 |
| Transaction type matches case type | +2 |

If multiple transactions tie for max score → `multiple_matches = true` → `relevant_transaction_id = null` → `evidence_verdict = insufficient_data`

#### 2d. Evidence Verdict Logic

```
No history                        → insufficient_data
Multiple equal matches            → insufficient_data (unless duplicate_payment)
No match found                    → insufficient_data
wrong_transfer + ≥2 prior txns    → inconsistent (established recipient pattern)
  to same counterparty
payment_failed + completed status → inconsistent (if no balance deduction mention)
  and complaint says only failed
pending cash_in/settlement        → consistent (delay case)
Matched + status/facts align      → consistent
```

#### 2e. Severity Determination

| Case Type | Logic |
|-----------|-------|
| phishing | always `critical` |
| wrong_transfer | `high` if ≥ 5000 BDT, else `medium` |
| duplicate_payment | `high` |
| payment_failed | `high` (balance deducted) |
| agent_cash_in_issue | `high` |
| merchant_settlement_delay | `medium` (merchant), `low` (non-merchant) |
| refund_request | `medium` if ≥ 5000 BDT, else `low` |
| other | `low` |

#### 2f. Human Review Escalation

`human_review_required = true` when ANY of:
- `is_phishing = true`
- `severity = critical`
- `case_type ∈ {wrong_transfer, duplicate_payment, agent_cash_in_issue}`
- `evidence_verdict = inconsistent`
- `amount ≥ 5000 BDT` (for any other case)
- `merchant_settlement_delay` with `amount ≥ 10000 or severity = high`

### Layer 3: Groq LLM

File: `lib/groq-client.ts`

- **Model:** `llama-3.3-70b-versatile`
- **Mode:** JSON Object mode (structural guarantees from Groq)
- **Temperature:** 0.1 (consistent, low creativity)
- **Max tokens:** 800

The LLM receives:
1. All ticket fields (complaint, channel, user_type, language)
2. Full transaction history
3. The pre-computed signals from the Rules Engine as authoritative context

The LLM is explicitly instructed to use the pre-computed `relevant_transaction_id` and `evidence_verdict` values — but since Layer 4 always overwrites them anyway, LLM hallucinations on these fields are structurally impossible.

If Groq fails (network error, timeout, rate limit), the service falls back to a `buildRulesFallback()` response using only rules engine data. **The service never returns 500 due to AI failure.**

### Layer 4: Deterministic Override

File: `lib/investigator.ts`

After the LLM responds, the Rules Engine's values unconditionally overwrite:
```ts
aiOutput.relevant_transaction_id = signals.matched_transaction_id;
aiOutput.evidence_verdict = signals.evidence_verdict;
if (signals.detected_case_type) aiOutput.case_type = signals.detected_case_type;
if (signals.suggested_department) aiOutput.department = signals.suggested_department;
if (signals.suggested_severity) aiOutput.severity = signals.suggested_severity;
if (signals.force_human_review) aiOutput.human_review_required = true;
```

This makes the 35% Evidence Reasoning score mathematically deterministic — no LLM can hallucinate the wrong transaction ID.

### Layer 5: Safety Sanitizer

File: `lib/safety.ts`

Final regex-based post-processor:

| Check | Pattern Type | Action |
|-------|-------------|--------|
| Credential request in reply | Regex with negative lookahead (won't flag "do not share") | Replace entire reply with safe template |
| Unauthorized refund promise | Flexible regex (handles "a full refund", "the refund") | Replace entire reply with safe template |
| Third-party redirect | Regex | Replace entire reply with safe template |
| External URLs | Regex `https?://...` | Replace with `[REMOVED_LINK]` |
| Missing PIN/OTP warning | String check | Append safety reminder |

The `customer_reply` field is guaranteed safe through 2 layers: the LLM's system prompt + the post-processor regex.

## 5. Bangla/Banglish Handling

- Unicode range `/[\u0980-\u09FF]/` detects Bengali script automatically (even without `language` field)
- Bangla keywords hardcoded in all detection arrays: `ভুল নম্বর`, `ক্যাশ ইন`, `টাকা কাটা গেছে`, `ওটিপি`, `পিন`, `এজেন্ট`, `রিফান্ড`, `টাকা ফেরত`
- Banglish phrases covered: `balance kete gese`, `payment hoise nai`, `cash in korsi`
- LLM instructed: "If `is_bangla` is true, write `customer_reply` in Bangla"

## 8. Known Limitations

1. **Bengali digit amounts not parsed from complaint text.** The amount-matching regex only captures ASCII digits (0-9). A complaint saying "২০০০ টাকা" won't yield an amount-based transaction match — type/keyword signals are used instead (which are still sufficient for correct matching in the sample cases).
2. **Time parsing is limited.** Relative times like "3pm" and "today" are handled, but complex phrases like "the day before yesterday evening" rely entirely on the LLM fallback.
3. **Ephemeral processing.** Transaction histories are processed in-memory per request. No database persistence.
4. **Single-request scope.** The system investigates one ticket at a time. It has no cross-ticket pattern analysis capability.
